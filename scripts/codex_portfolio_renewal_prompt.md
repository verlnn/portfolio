# Codex Prompt — Portfolio Renewal (Vite React SPA)

## 목표

기존 포트폴리오 웹의 **기능과 콘텐츠는 유지**하면서, **디자인과 정보 구조를 전면 리뉴얼**한다.  
결과물은 **대기업, 중소기업, 강소기업, 유니콘, 스타트업의 인사담당자, 실무 면접관, 임원**이 보더라도 신뢰감과 호감을 느끼고, 실제 면접으로 이어질 수 있는 수준의 **채용 친화형 포트폴리오**여야 한다.

이 포트폴리오는 단순한 프로젝트 전시 사이트가 아니라, 아래 질문에 즉시 답해야 한다.

> **왜 이 개발자를 면접에 불러야 하는가?**

---

## 현재 기술/구조 정보

현재 포트폴리오는 **React SPA 기반**이다.

- `index.html`에서 `/src/main.tsx`를 로드
- `package.json` 스크립트는 **Vite** 기준으로 동작
- `src/app/layout.tsx` 같은 **Next.js 관련 파일과 `next` 의존성은 일부 남아 있으나 현재 빌드/실행 경로에서는 사용되지 않음**
- 따라서 이번 작업은 **Vite 기반 React SPA를 기준으로 진행**
- Next.js로의 마이그레이션은 하지 말 것
- 현재 동작 중인 기능, 데이터, 섹션은 유지할 것

---

## 절대 규칙

1. **기존 기능 제거 금지**
2. **기존 콘텐츠 삭제 금지**
3. **기존 링크/CTA/연락처/프로젝트 데이터 유지**
4. 목표는 **디자인 리뉴얼 + 정보 구조 개선 + UX 개선**
5. 필요 시 컴포넌트 분리/정리는 가능하지만, 사용자 입장에서 기존 핵심 정보가 사라지면 안 됨
6. 현재 SPA 구조를 존중하고, **실행 가능한 상태로 리팩터링**
7. 디자인은 반드시 **Toss 스타일의 신뢰감 있는 미니멀 UI**를 지향
8. “예쁘게”보다 **채용 전환율이 높아지는 구조**를 우선
9. 모든 변경은 **읽기 쉬움, 신뢰감, 실무감, 문제 해결 역량 전달**에 기여해야 함

## 현재 섹션 구조

현재 포트폴리오는 아래 구조를 가진다.

1. 상단 네비게이션 `SectionNav`
2. 히어로/소개 `Hero`
3. 자기소개 `About`
4. 경력/재직 기간 요약 `Experience`
5. 재직 중 회사 프로젝트 `CompanyProjects`
6. 개인/사이드 프로젝트 `Projects`
7. 기술 스택/스킬 `Skills`
8. 연락처 `Contact`

---

## 리뉴얼 핵심 방향

현재 구조는 일반적인 개발자 포트폴리오 흐름에 가깝다.  
하지만 채용 관점에서는 **“자기소개 → 문제 해결 역량 → 실무 경험 → 프로젝트 → 기술스택 → 연락”** 순서가 더 강하다.

이번 리뉴얼에서는 **기존 섹션을 최대한 활용하되, 배치/강조/디자인을 채용 친화적으로 재구성**해야 한다.

## 최종 권장 정보 구조 (합격률 극대화 버전)

아래 순서를 기준으로 리뉴얼하라.

### 1. Sticky Top Navigation
- 기존 `SectionNav` 유지
- Toss 스타일로 리디자인
- 현재 활성 섹션 하이라이트
- 스크롤 시 부드럽고 고급스러운 인터랙션
- 모바일에서도 읽기 쉬운 축약형 구조
- 과한 장식 금지, 얇고 정제된 느낌

---

### 2. Hero Section — 첫 5초 설득
기존 `Hero`를 리뉴얼한다.

첫 화면에서 반드시 전달해야 할 것:

- 이름
- 직무: **백엔드 개발자**
- 한 줄 가치 제안
- 핵심 강점 3~4개
- CTA

전달 메시지 예시 방향:

- 안정적인 운영과 확장 가능한 시스템을 만드는 백엔드 개발자
- 문제를 구조적으로 분석하고 운영 가능한 해결책까지 설계하는 개발자
- 서비스 운영, 데이터, 성능, 협업을 함께 보는 개발자

UI 요구:
- Toss 스타일의 넓은 여백
- 대형 타이포
- 짧고 강한 문장
- 핵심 키워드 강조
- CTA 버튼 1~2개
- 스크롤 유도 요소는 과하지 않게

---

### 3. Self Introduction / Resume Summary — 가장 먼저 읽히는 자기소개
기존 `About`을 페이지 상단 핵심 섹션으로 승격한다.

이 섹션은 “자기소개”가 아니라 **채용용 요약문**처럼 보여야 한다.

목표:
- 인사/면접관이 가장 먼저 읽는 본문
- 지원자의 일하는 방식, 문제 해결 관점, 운영 철학을 짧고 강하게 전달
- 긴 문장 덩어리보다 읽기 좋은 단락 구조
- 중요한 문장은 시각적으로 강조

디자인 요구:
- 본문 폭을 적절히 제한하여 가독성 극대화
- 주요 문장을 콜아웃 박스/강조 텍스트로 표현 가능
- 이력서 요약처럼 안정감 있고 신뢰감 있는 레이아웃
- 너무 감성적이거나 블로그형 문체 금지

---

### 4. Core Strengths / Why Hire Me
**새 섹션 추가 가능.**  
기존 콘텐츠를 활용해 “왜 이 개발자를 뽑아야 하는가”를 구조화한다.

추천 카드 주제:
- 문제 해결
- 운영 안정성
- 시스템 설계
- 성능 개선
- 협업/커뮤니케이션

각 카드에는 아래가 들어가면 좋다.
- 짧은 제목
- 한 줄 설명
- 가능한 경우 수치/성과/키워드

예:
- 성능 병목 분석 및 개선
- 운영 장애 원인 파악 및 우회 구조 설계
- 확장 가능한 API/도메인 구조 설계
- 현업/동료와의 협업 기반 문제 정리

이 섹션은 채용담당자 입장에서 매우 중요하다.  
프로젝트보다 먼저 보아도 납득 가능한 수준으로 설계하라.

---

### 5. Experience — 경력 요약을 더 전략적으로 재구성
기존 `Experience`는 단순 재직 기간 나열이 아니라, **실무 신뢰도를 강화하는 섹션**으로 바꾼다.

포함해야 할 것:
- 총 경력 연차
- 주요 도메인/산업군
- 운영/개발 환경
- 담당 역할 키워드

예시 방향:
- 병원/의료 데이터 시스템 경험
- 운영 중인 서비스 유지보수 및 고도화
- 인증/권한, 데이터 연계, 성능 이슈 대응
- 협업 기반 개발 및 운영 대응

UI:
- 단순 타임라인도 가능
- 또는 카드형 요약 + 상세 확장 구조도 가능
- 읽는 사람이 “실무를 해본 사람”으로 즉시 인식하게 만들 것

---

### 6. Company Projects — 가장 강한 실무 프로젝트를 먼저
기존 `CompanyProjects`는 가장 중요한 섹션 중 하나다.

리뉴얼 방향:
- 단순 프로젝트 나열 금지
- 각 프로젝트마다 **문제 / 역할 / 기술 / 결과**가 드러나야 함
- 실무감이 느껴지도록 구성

프로젝트 카드/섹션에 포함:
- 프로젝트명
- 프로젝트 한 줄 설명
- 담당 역할
- 사용 기술
- 핵심 문제 해결 포인트
- 가능하면 정량적/정성적 결과
- 운영 환경/도메인 특성

강조해야 할 포인트:
- 실제 운영 서비스 경험
- 복잡한 요구사항 조율
- 데이터 처리/연계
- 안정적인 시스템 운영
- 병목 해결, 구조 개선, 운영 대응

시각적으로는 Toss 스타일 카드 기반으로 구성하되,  
정보량이 많아도 지저분해 보이지 않도록 계층을 분명히 하라.

---

### 7. Engineering Impact / Problem Solving
**새 섹션으로 추가하거나 Company Projects 내부에서 분리 강조 가능**

이 섹션은 포트폴리오의 핵심이다.  
대부분의 개발자 포트폴리오는 여기서 무너진다.  
단순히 “무엇을 만들었다”가 아니라 **어떤 문제를 어떻게 해결했는지**를 보여줘야 한다.

이 섹션에서 보여줄 내용:
- 성능 개선 사례
- 운영 장애 대응 사례
- 아키텍처/구조 개선 사례
- 협업을 통한 문제 정의 및 해결 사례

형식 예시:
- 문제 → 행동 → 결과
- Before / After
- 병목 원인 / 개선 방식 / 기대 효과

디자인:
- 작은 케이스 스터디 카드
- 혹은 강조 블록
- 너무 길면 아코디언/모달/펼침 구조 고려
- 채용자가 빠르게 훑어도 강점이 남도록 만들 것

---

### 8. Side Projects — 개인 프로젝트는 “실행력” 관점으로
기존 `Projects`는 유지하되, 회사 프로젝트보다 뒤에 둔다.

리뉴얼 방향:
- 개인 프로젝트를 단순 취미가 아니라 **문제 해결과 실행력의 증거**로 보이게 설계
- 아이디어보다 구현/설계/확장성 관점 강조
- 프로젝트 수가 많다면 중요도 순 정렬

각 프로젝트에 포함:
- 프로젝트명
- 해결하려는 문제
- 핵심 기능
- 기술 스택
- 아키텍처/설계 포인트
- 배운 점이 아니라 **직무 활용 가능성** 중심 설명

### 9. Skills & Technologies — 단순 기술 나열을 넘어서
기존 `Skills` 섹션 유지하되, 디자인과 분류를 대폭 개선한다.

현재 카테고리:
- Frontend
- Backend
- Tools & Others
- Currently Exploring

리뉴얼 방향:
- Toss 스타일 태그/칩 UI
- 가독성 좋은 그룹 카드
- 기술 수준/사용 맥락이 보일 수 있도록 최소한의 보조 설명 고려
- 예: “실무 사용”, “운영 경험”, “학습 중”

중요:
- 기술이 많아 보여도 산만하면 역효과
- 핵심 기술이 먼저 보이게 정렬
- 백엔드 지원자답게 **Java / Spring / DB / 운영 기술**이 확실히 중심에 오도록 구성

### 10. Contact / CTA
기존 `Contact`는 마지막 전환 섹션으로 강화한다.

목표:

포함:

예시 방향:

## 디자인 시스템 요구사항 (Toss 스타일)

반드시 아래 분위기를 구현하라.

### 전반적 톤
- 깨끗한 흰색 배경
- 절제된 포인트 컬러
- 라운드 카드
- 부드러운 그림자
- 강한 타이포 위계
- 넓은 여백
- 안정감 있는 정렬
- 신뢰감 있는 인터랙션

### 타이포그래피
- 헤드라인은 크고 명확하게
- 본문은 읽기 편한 폭/행간 유지
- 시선 흐름이 자연스럽게 이어져야 함
- 중요 문장은 강조하되 과장되지 않게

### 컴포넌트 스타일
- 카드형 섹션
- 섬세한 hover / reveal animation
- 지나친 glassmorphism 금지
- 과한 gradient 금지
- 포트폴리오가 아닌 **제품급 서비스 UI**처럼 보이게

### 반응형
- 데스크톱/태블릿/모바일에서 모두 자연스러워야 함
- 특히 모바일에서 텍스트 덩어리가 답답하지 않아야 함

## UX 요구사항

1. 첫 화면에서 지원자의 정체성이 즉시 보여야 함
2. 자기소개가 프로젝트보다 먼저 읽혀야 함
3. 정보 밀도는 높되 읽기 부담은 낮아야 함
4. 채용담당자가 30초만 훑어도 강점이 남아야 함
5. 실무 면접관이 봐도 “실제 운영 경험이 있구나”가 드러나야 함
6. 임원이 봐도 신뢰감 있고 정돈된 인상을 받아야 함

---

## 구현 요구사항

- 기존 Vite React SPA 구조를 유지
- 필요 시 컴포넌트 재구성
- 재사용 가능한 UI 컴포넌트로 정리
- 폴더 구조를 정돈
- 스타일 시스템 일관성 확보
- 불필요한 레거시/미사용 코드(예: 현재 실행 경로에 쓰이지 않는 Next 관련 잔재)는 **실행에 영향이 없는 범위에서 정리 제안 가능**
- 단, 실제 제거 시에는 기존 동작 영향 여부를 명확히 판단할 것

예시 구조:

```text
src/
  components/
    navigation/
    hero/
    resume/
    strengths/
    experience/
    projects/
    skills/
    contact/
    common/
  sections/
  data/
  styles/
  hooks/
  utils/
```

## 특히 중요한 점

이 포트폴리오는 “예쁜 개인 사이트”가 목표가 아니다.  
목표는 **서류 통과율과 면접 연결 가능성을 높이는 것**이다.

따라서 결과물은 아래 인상을 반드시 줘야 한다.

- 이 사람은 실제 운영 경험이 있다
- 이 사람은 문제를 구조적으로 푼다
- 이 사람은 협업과 유지보수를 이해한다
- 이 사람은 백엔드 개발자로 신뢰할 수 있다

- 디자인, 정보 구조, 레이아웃, 타이포그래피, 컴포넌트 구조를 개선하여
